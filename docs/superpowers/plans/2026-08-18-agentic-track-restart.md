# SIDR — переход от умного роутера к агентной системе

> **STATUS: APPROVED (владелец, 2026-08-18).** Стратегический маршрут агентного трека, не план блока.
> Снимает развилки, блокировавшие A1–A6 с 2026-07-11. Этапы 1/0/2/3 исполнимы по этому документу;
> Этапы 4–7 заходят обычным циклом `brainstorm → spec → plan → build`. См. §«Как использовать этот документ».

## Context

**Зачем этот план.** Sidr прошёл Stage 1 (AI-Launcher MVP) и весь дизайн-трек DS-1…DS-11 + I18N-1.
Инженерная база сильная: `:domain` чист (stdlib+coroutines, проверяется каждый блок), приватность
выражена исполняемыми guard-тестами, каждый блок закрывается ADR + приёмкой на устройстве.

Но заявленная цель — агентная ОС — не начата. Собственный ADR от 2026-07-10 постановил «next
architectural slice = A1»; спеки A1–A6 написаны 2026-07-11. За 5,5 недель после этого закрыто шесть
дизайн-блоков и **ноль агентных**; все шесть планов A1–A6 до сих пор `STATUS: PROPOSED`.

Причина структурная: у дизайн-трека есть Master Plan (2087 строк), милстоуны, DoD, change-control —
он всегда «готов к следующему блоку». У агентного трека — шесть спек и четыре нерешённые развилки, он
всегда «требует решения». Трек с бо́льшим процессом выигрывает независимо от важности. Этот план
устраняет эту асимметрию и снимает четыре развилки.

**Что конкретно мешает движку сегодня:**

1. **У агента нет рук.** `DefaultActionCatalog` — 7 действий, 5 из них «открыть что-то у себя».
   Многошаговый план поверх этого даёт «открой приложение → открой приложение».
2. **Понимание заперто за префиксным матчером.** `RuleBasedIntentMatcher` = 7 глаголов
   (`open/launch/start`, `install`, `search/find/google`) + 2 ключа настроек + 7 строк команд.
   Правило «LLM консультируется только при low-confidence» означает, что модель никогда не видит
   задачу целиком. Многошаговые цели структурно не проходят этот фильтр.
3. **Матчер понимает только английский.** Все константы — английские литералы. На устройстве
   владельца (системная локаль `ru-RU`, интерфейс русский) «открой телеграм» → `UnknownIntent`
   confidence 0.10; `llmRouterEnabled` по умолчанию `false` ⇒ **русская команда офлайн не работает
   вообще.** `LocaleCompletenessGuardTest` это не ловит: он проверяет `strings.xml`, а константы
   матчера — hardcoded Kotlin-множества в `:data:repository`.
4. **~1400 строк инертного ONNX** едут в каждом APK. OQ#1/#2 открыты 14 месяцев. Классификатор на
   7 меток не извлекает аргументы (это делает `SlotExtractor` регуляркой) и по построению
   ограничен до подсказки (`NluConfidenceCalibrator` мапит в `[0.50, 0.85)`).
5. **Платформа ушла вперёд.** `AppFunctions`, `MCP`, `Gemini Nano`, `AICore`, `ADK` — ноль
   упоминаний во всей документации.
6. **Цель «ПК» отсутствует в доках**, а решение по портируемости ядра дешевеет только сегодня.

**Ожидаемый результат.** Работающий агентный движок: цель → план → гейт → инструмент → наблюдение →
результат → трассировка, с руками из реестра ОС, портируемым ядром и сохранением всех инвариантов
приватности и согласия.

## Новое правило вместо «rule-first before any LLM call»

Заменяет формулировку в `CLAUDE.md` (Hard rules) и `docs/architecture.md` (Principles):

```
Понимание принадлежит модели. Исполнение принадлежит детерминированному слою.

1. FastPath (детерминированный, локализованный) отвечает на частотные точные команды
   без модели. Это оптимизация задержки, НЕ фильтр понимания.
2. Кэш выученных планов воспроизводит уже понятые формы целей детерминированно и офлайн.
3. Всё остальное идёт к планировщику-модели. Промах FastPath больше НЕ является
   основанием ответить «Unknown command».
4. Ничто из предложенного моделью не исполняется, не получает прав и не покидает
   устройство иначе как через детерминированные ворота:
   ToolRegistry → валидация аргументов → preconditions → риск-гейт/consent →
   границы цикла → egress allow-list → трассировка.
5. Router-off / offline / no-key ⇒ FastPath + кэш планов + честное «нужна сеть».
   Байт-в-байт паритет rule-only остаётся проверяемым тестом.
```

**Следствие, требующее решения внутри Этапа 1:** `FeatureFlags.llmRouterEnabled` (сейчас `false`)
перестаёт быть воротами понимания. Рекомендация — понимание доступно, когда сконфигурирован
провайдер; явный переключатель «только локально» сохраняется для пользователей, которым он нужен.

## Правило роста: функционал масштабируется, границы — нет

Замысел владельца — наращивать функционал по мере роста потребностей, не фиксируя облик системы
заранее. Это принимается и распространяется на поверхность (UI появляется вслед за способностью) и
на абстракции (обобщать при появлении второго потребителя, а не в предвкушении — существующий
принцип feature-first).

Из этого правила **исключаются границы**. Реестр как единственный путь к миру, валидация аргументов,
гейт согласия, лимиты цикла, трассировка, egress allow-list и откат закладываются на **первом же
срезе, для двух инструментов** — не «когда понадобится». Причина механическая: если рантайм сначала
научился вызывать 20 инструментов, а согласие добавляется потом, это 20 мест, где его можно забыть.
Если согласие живёт внутри `ToolExecutor` с первого дня, инструмент №21 получает его бесплатно.
Та же логика, по которой guard-тесты приватности в этом проекте написаны до того, как появилось что
утекать.

## Как использовать этот документ

Это **не** план блока в смысле репозитория (`docs/superpowers/plans/*.md` = пронумерованные задачи с
файлами и тестами, по которым идёт сессия). Он стоит **выше спек**: снимает развилки, блокировавшие
агентный трек с 2026-07-11, и задаёт очередь блоков.

```
CLAUDE.md → decisions.md (ADR) → specs/*.md → plans/*.md (Task 1..N) → сессия → гейт + ADR
                    ▲
            этот документ решает, ЧТО и в каком порядке сюда попадает
```

| Этап | Исполним по этому документу? |
|---|---|
| 1 (стратегические ADR), 0 (расчистка), 2 (тулчейн + KMP), 3 (агентный Master Plan) | **Да** — файлы и содержание определены |
| **4.0 (инверсия флага понимания)** | **Да** — радиус и файлы определены; четыре развилки спрашиваются у владельца в начале сессии |
| 4–7 (A0, A1′, A4′, A2/A3, A5/A6) | **Нет** — каждому нужна своя спека и свой план с задачами, обычным циклом `brainstorm → spec → plan → build` |

Кикофф сессии (по образцу `ai-launcher-mvp-plan.md` §0):

```
Работаем над Этапом <N> из docs/superpowers/plans/<этот-файл>.md.
Прочитай CLAUDE.md (Hard rules) и §«Решения владельца» + раздел нужного этапа.
Этап закрывается зелёными testDebugUnitTest + assembleDebug, записью ADR
и синхронизацией CLAUDE.md / current-status.md.
```

**Порядок: Этап 1 идёт первым.** Стратегические решения фиксируются до кода — прецедент AIL-4, где
блокирующий ADR писался перед реализацией. В частности 0.3 (удаление 1400 строк ONNX) исполняет
решение ADR №2; без него это было бы оправдание задним числом.

### Почему коммит, а не «оставлю в дереве»

Гранулярность — **не сессия, а наименьшее самосогласованное состояние**. В I18N-1 это дало ~28
коммитов за 8 дней при 16 задачах; иногда 4–5 за сессию, иногда ноль (аналитической сессии коммитить
нечего).

Коммит в агентной работе покупает три вещи:

1. **Восстановление.** 2026-08-18 в этом репозитории: незакоммиченный черновик плана был перезаписан
   и потерян навсегда; `LocaleCompletenessGuardTest` (+96 строк) в том же дереве уцелел, потому что
   был закоммичен (`bce726c`). Одинаковый риск, разный исход — разница только в коммите.
2. **Поверхность ревью.** `.superpowers/sdd/` состоит из `review-<sha>..<sha>.diff` — ревьюер-агент
   смотрит диff между коммитами. Нет коммитов — нет ревью.
3. **Передача контекста.** `git log --oneline -5` — самый дешёвый handoff. Поэтому качество
   сообщений (conventional commits + скоуп блока) не церемония, а рабочий канал.

**Не коммитить:** при красном гейте (чинить или парковать на scratch-ветке) и при выбрасываемой
разведке.

**Экспозиция:** ветка `launcher--7` на 2026-08-19 была на 38+ коммитов впереди `codeberg/launcher--7`
и не запушена. Пуш — решение владельца, но пока его нет, локальный git остаётся единственной копией.

### 0.1. ✅ ЗАКРЫТО (2026-08-19) — релиз разблокирован

Владелец выполнил ревью по пакету
`docs/superpowers/specs/2026-08-11-i18n-1-owner-review.md` и распорядился вписать маркер; агент вписал
`OWNER-REVIEWED 2026-08-19` в 10 файлов `values-{ru,tr}/strings_locked.xml` (5 модулей), **записав в
шапке каждого файла, что ревью выполнил владелец, а токен напечатал агент по его указанию** — гейт эти
два случая различить не может, поэтому это сказано в самом файле.

**Найдено и починено до подписи:** пакет ревью не перечислял 5 ключей `launcher_prayer_name_*`,
добавленных I18N-2 уже после его написания, — то есть файл, который гейт просил подписать, содержал
строки, которых документ не показывал. Добавлена Section 6e; их текст сверен побайтно с Section 1b
(brief-verbatim) и идентичен, так что стоимость ревью действительно нулевая — но узнать это из пакета
было нельзя. Полная сверка показала, что это была единственная непокрытая дыра.

**Проверка (JDK-17, exit 0):** `:app:checkOwnerReviewedLocaleStrings` BUILD SUCCESSFUL;
`:app:assembleRelease` BUILD SUCCESSFUL — **первый релизный артефакт в истории проекта**.

**Побочный замер, нужный 0.3:** `app-release-unsigned.apk` = **78 МБ**, из них **ONNX 70.4 МБ** (8
записей, 4 ABI) — ~90% артефакта занимает рантайм, который ни разу не исполнялся. Для AAB на одно
устройство это ~18,5 МБ (arm64-v8a). Записано как база «до» в ADR 2/4.

**Остаётся открытым (не чинится здесь):** гейт проверяет **наличие** маркера, а не **покрытие**. Теперь,
когда все 10 файлов подписаны, следующий блок может молча добавить в них Class B ключ — гейт не
сработает. До сегодняшнего дня пробел спал (подписанных файлов было ноль); подпись перевела его в
активный. Честная починка — маркер, привязанный к хешу Class B содержимого файла.

### 0.2. ✅ ЗАКРЫТО (2026-08-19) — FastPath локализован на ru/tr

**Результат.** `RuleBasedIntentMatcher.kt` — единственный файл, названный этим разделом — получил
`ru`/`tr` формы для всех пяти словарей (`LAUNCH_VERBS`/`INSTALL_VERBS`/`SEARCH_VERBS`/
`SETTINGS_KEYWORDS`/`SIMPLE_COMMANDS`). Потребовались два структурных изменения сверх «добавить
слова в множества», оба продиктованы собственным примером проверки этого раздела («telegramı aç»
обязан давать тот же интент, что «open telegram»): (1) формы глаголов стали locale-tagged
(`VerbForms(prefixByLocale, suffixByLocale)`), а не плоским `Set<String>` — иначе
`FastPathLocaleGuardTest` не может спросить «есть ли форма для `tr`»; (2) турецкий — SOV
(глагол-финальный: «telegramı aç», не «aç telegram»), поэтому рядом с существующим
prefix-механизмом появился suffix-механизм (`input.endsWith(" $verb")`) — плоское
англо-русское множество структурно не может распознать глагол-финальную конструкцию.
`CommandNormalizer.normalize` не тронут — уже лужит `Locale.ROOT` (турецкая İ/ı корректна).
**Сознательно не сделано, задокументировано:** турецкие падежные суффиксы (аккузатив «-ı» в
«telegramı») не срезаются с извлечённого имени приложения — полная морфология вне объёма этапа
(«дни, не недели»); задокументировано в KDoc матчера как известное ограничение, не выдано за тихо
починенное. Реальная device-регрессия («открой телеграм» на `ru-RU`) от этого не зависит — глагол
не распознавался вовсе, а не падало извлечение Cyrillic-имени. Новый
`FastPathLocaleGuardTest` (`:data:repository`, по образцу `LocaleCompletenessGuardTest`, читает
Kotlin-константы напрямую — это не UI-строка) красный, если у любого множества нет формы для
`en`/`ru`/`tr`. `RuleBasedIntentMatcherTest` получил табличный parity-тест (ровно примеры из
раздела «Проверка» ниже) + точечные тесты на ru/tr install/settings/simple-commands/bare-verb;
34 → 43 теста. **Гейт (JDK-17, не через `tail`):** `:data:repository:testDebugUnitTest` зелёный;
корневой `testDebugUnitTest assembleDebug` BUILD SUCCESSFUL (543 задачи); `:core:ui:
verifyRoborazziDebug` BUILD SUCCESSFUL (голдены не тронуты — ожидаемо, в разделе нет UI).
`git diff --stat`: ровно названный файл + два тестовых файла. ADR «2026-08-19 — Этап 0.2 complete —
FastPath localized to ru/tr» в decisions.md.

   - единый доступ к NPU всех крупных чипсетов через `CompiledModel API` (LiteRT 2.x), JIT-подход —

   constrained decoding в него не входят — это рантайм, слой приносишь сам; и его главное
   преимущество (свой PyTorch-пайплайн) в проекте отсутствует — PyTorch здесь ноль.
   **Условие переключения:** появление собственного дообучения планировщик-модели на своих данных
   (кэш выученных планов — естественный источник пар «цель → план»). Тогда PyTorch → fine-tune →

   `AICore` / Gemini Nano — отдельный путь для устройств, где он есть: модель живёт в системном
   процессе, heap приложения не тратится вовсе; ограничение — железо.

   Фиксирует причину, по которой локальность достигается **кэшем планов, а не моделью в процессе**:
   не конкретное число бюджета, а порядок величины и роль процесса. 1B-модель в int4 — 700 МБ–1 ГБ
   резидентно; лаунчер обязан мгновенно воскрешаться, а самый тяжёлый процесс LMK убивает первым.

   иной — 200–500 МБ, вес может быть memory-mapped. В сочетании с 0.6 это переводит локальное

   правку `docs/architecture.md`, а не молчаливое ослабление. И правит `docs/adr/ADR-001-hybrid-ai.md`

3. **Portable core boundary** — что именно составляет «Framework»: `domain/agent`, `domain/tool`,

## Этап 6 — A4′ Рантайм полностью

### Модель исполнения: лаунчер — процесс, агент — сессия

Не разобрано ни в одной из шести спек, при этом определяет форму продукта. Специфичная для Android
ловушка: **собственное действие агента выбрасывает пользователя из процесса, где агент живёт.**

```
Шаг 1: открыть Календарь → пользователь в Календаре → лаунчер в фоне → процесс может быть убит
Шаг 2: ...                 кто исполняет?
```

Для обычного лаунчера это норма — он своё отработал. Для агента это ломает цикл в **типичном**, а не
краевом случае.

**Ответ — четыре слоя:**

1. **Корректность (обязательна, от процесса не зависит).** `AgentSession` сохраняется после каждого
   перехода состояния. Смерть процесса = прерывание того же класса, что ожидание согласия → `Paused`.
   При возврате пользователя сессия восстанавливается и предлагает продолжить. Возобновление
   идемпотентно. Механика уже требуется спекой A4 («persisted, inspectable state machine»,
   «duplicate resume/confirm cannot execute a step twice») — теперь ясно, зачем.
2. **Удобство (пока процесс жив).** Цикл крутится в существующем `@ApplicationScope`
   (инжектится в `SidrLauncherApp`). Переживает уничтожение Activity, поворот, уход в фон без
   убийства. Обычный случай, без церемоний.
3. **Непрерывность (только когда шаг обязан продолжаться, пока человек в другом приложении).**
   Foreground service с обязательным уведомлением — единственный честный механизм в Android, и он
   совпадает с доктриной: видно, что работает, можно остановить. `android-limitations.md` разрешает
   ровно этот случай («justified and user-visible»).
4. **Никогда.** Фоновые автономные циклы без видимости — уже в non-goals спеки A4, оставить.

**Отдельный процесс агенту не нужен.** Рантайм — машина состояний и несколько объектов, это байты;
единственное тяжёлое в системе (модель) по построению вне процесса (облако либо AICore).
`android:process=":agent"` добавил бы IPC, второй граф Hilt и вторую точку отказа ради экономии байтов.

### Три спеки, которых нет ни в одном документе

1. **Откат и компенсация.** A4 упоминает `PartiallyCompleted` как состояние — и всё. «Шаг 3 из 5
   упал, шаги 1–2 уже изменили мир» не заспецифицировано нигде. Дизайн-док про это говорит
   («Aftermath / undo surface»), домен молчит.
2. **Протокол уточнения.** `PlanResult.Clarify(question)` — терминальный лист. Многоходового
   «агент спросил → человек ответил → план уточнён → продолжили» нет ни в одном контракте.
3. **Кэш выученных планов** — механизм локальности из решения #2. Обобщает
   `ResolutionPreferenceStore` (S2-1) и `AliasStore` (S2-2) с одного действия до плана: цель понята
   моделью один раз → сохраняется шаблон плана (не формулировка) → воспроизводится детерминированно,
   офлайн, на любом железе. Многоязычно бесплатно: шаблон привязан к плану, формулировки
   накапливаются вокруг.

## Этап 7 — A2 / A3 по потребителю, затем A5 / A6

**Спеки A2 и A3 остаются целиком — они написаны верно.** Потребитель у них назван и существует по
замыслу: это `Planner` из спеки A4 (`plan(goal, ContextSnapshot, ToolRegistry, UserMemory)`).
`agentic-os-architecture.md` прямо определяет себя как «direction, not a committed plan» — описывать
целевую форму целиком и есть работа архитектурной спеки, иначе A1 примет решения, блокирующие A2.

Риск не в том, что форма описана, а в том, что спека потом читается как **список к постройке**.
В репозитории есть оба исхода:

| Прецедент | Что сделали | Результат |
|---|---|---|
| **AIL-1** | «ships only the contract + the family vocabulary; the concrete catalog + impl is deferred to AIL-2» | Потребитель пришёл через день, всё сошлось |
| **`:data:ai-local`** | Построено полностью (`ModelStore`, `ModelProvisioner`, `Sha256Verifier`, `KtorModelDownloader`, `ModelDownloadWorker`, `Scheduler`) против `ModelDownloadConfig.INTENT_NLU_PENDING` | Потребитель не пришёл за 14 месяцев; 1400 строк и AAR в каждом APK — удаляются в 0.3 |

Разница не в качестве спеки, а в том, что решил план.

**Правило для A2/A3:** словарь и контракты — целиком (паттерн AIL-1); реализуется только то, что
читает первый планировщик A4; непостроенное помечается в спеке как «спроектировано, не построено,
триггер постройки — <какой>».

### Обязательное проектное решение A2: двойная проекция контекста

Принимается **при проектировании A2, не после** — задним числом это переделка всего слоя контекста,
сейчас стоит почти ничего.

```
ContextEngine
  ├── projectForCloud(snapshot) → узкая, редуцированная, под OutboundContextPolicy
  └── projectForLocal(snapshot) → широкая: сырые данные, НИКОГДА не покидающие устройство
```

**Почему это не преждевременная абстракция, а следствие уже принятых решений.**
`OutboundContextPolicy.ALLOWED` содержит ровно четыре значения — `USER_COMMAND`,
`STATIC_SYSTEM_PROMPT`, `GENERATION_LIMITS`, `ACTION_CATALOG_SCHEMA`. Это значит, что **облачный
планировщик планирует вслепую**: он не видит календарь, местоположение, список приложений и память.
То есть приватностная архитектура проекта — работающая и правильная — **структурно ограничивает
потолок полезности облачного планировщика**, потому что именно эти данные делают агента личным
(«найди свободный вечер», «успею ли до магриба», «открой то, чем я обычно пользуюсь сейчас»).

Спека A2 эту напряжённость чувствует и предлагает компромисс — расширить allow-list на
*редуцированные* поля снимка. Локальной модели компромисс не нужен: ей можно отдать сырой календарь
целиком, потому что ничего не уходит с устройства. **Это и есть настоящая причина, по которой
серьёзной агентной системе нужен локальный вывод — не офлайн и не цена, а доступ к личному
контексту.**

Следствия:
- проекции две с первого дня, даже пока локального планировщика нет — тогда он подключается, а не
  требует переделки;
- `projectForLocal` по построению никогда не проходит через egress-слой; guard-тест обязан это
  доказывать (кандидат в `DOC-AML-*` доктринальной матрицы);
- порт `Planner` (`TemplatePlanner → LocalPlanner → LlmPlanner` в спеке A4) уже резервирует место —
  задача A2 в том, чтобы контекст был готов его наполнить.

Локальный планировщик записывается как **назначенный уровень с зарезервированным швом**, а не как
«ускоритель, может быть, когда-нибудь». Второе при реализации игнорируют.

**Почему здесь цена лишнего поля выше обычной.** Каждое поле `ContextSnapshot` обязано пройти
классификацию в `OutboundContextPolicy`, получить guard-тест против утечки сырых данных, быть
permission-gated и fault-isolated отдельно, и пережить приватностное ревью в каждом последующем
блоке. Неиспользуемое поле здесь — не мёртвый код, а постоянное обязательство в самом чувствительном
слое. То же с A3: `MemoryConflict`/`MemoryMutation` подразумевают политику разрешения конфликтов,
которую до появления конфликтующего писателя пришлось бы писать против воображаемых случаев.

Переиспользовать: существующие `SuggestionProvider`-ы уже fault-isolated и permission-gated —
готовые провайдеры контекста; `ResolutionPreferenceStore` (S2-1) и `AliasStore` (S2-2) — два
реальных хранилища памяти для унификации.

A5/A6 — только после того, как A4 выдаёт реальные трассы.

### PREVIEW-поверхности — остаются (решение владельца, 2026-08-18)

Пять `PREVIEW`-вкладок (Tasks / Agents / Activity / Terminal / Interaction Moments) **не удаляются**.
Бейдж `PREVIEW` — это в точности мера, предписанная аудитом (§21, Риск 4: «roadmap должен пометить
их `AVAILABLE NOW` / `FOUNDATION` / `FUTURE CONTRACT`»), поэтому golden rule не нарушен. Слоты в
таб-баре резервируют место и заранее учат пользователя форме — когда A4 приедет, вкладка не
появляется внезапно.

Снимается не сама поверхность, а налог на сопровождение — сейчас решение о превью принимается заново
в каждом сквозном блоке (DS-11 — проверка cmap ради маркера `•`; I18N-1 — отдельное owner-решение об
исключении из локализации; дальше по очереди a11y, темы, матрица goldens, fontScale):

1. **Политика, записанная один раз:** PREVIEW-поверхности по умолчанию исключены из сквозной работы
   (i18n, a11y, goldens, темы). Вопрос перестаёт задаваться в каждом блоке.
2. **Срок годности у каждой вкладки:** `tasks` / `agents` → реальны в A4, `activity` → в A5,
   `terminal` / `interaction moments` → назвать блок или пометить бессрочным демо. Иначе превью
   незаметно становится постоянной мебелью.
3. **Устранить расхождение в доках:** DS-0 фиксирует «target IA = 4 поверхности, 5-табовая навигация
   отложена до A4», а шипнутый `SidrTabBar` уже имеет пять вкладок (`home/apps/tasks/agents/activity`).
   Обновить DS-0 под фактическую IA либо явно записать три слота как резерв.
4. **Оговорка на A4:** когда движок приедет, поверхность определяет он, а не нарисованный макет.

не рисуется в `AwaitingConsent` (двухшаговость видна только в `Paused` и `Completed`); «План выполнен»
значит «все шаги исполнены», а не «цель достигнута»; приёмка пункта 8 потребовала агентского
вмешательства, то есть проверяет движок, а не продукт.

### Что сделал A0.5, и что он оставил у двери A1′

**Закрыт `CODE-GREEN` 2026-08-26.** `:consumer:jvm` — обычный `kotlin.jvm`-модуль с **нулём
Android-артефактов** на разрешённом classpath — прогоняет одну цель через `goal → plan → gate → tool →
observe → tool → result → trace` поверх **неизменённых** контрактов движка. Весь след блока в `commonMain` — **две**
правки в двух файлах: значение `GoalShape.Free` и вынужденный им арм `NoPlan` в `TemplatePlanner`. Гейт: 1219 тестов, 0 падений. ADR
«2026-08-26 — Этап 4.5 (A0.5)».

**Четыре словарные находки ждут у двери A1′, и ни одна не является дефектом, ждущим починки:**
`ObservedFact` (целый класс реальности невыразим — §6.3, ниже), `CommandFailure`, `StepRationale`,
`ArgType` (одно значение, поэтому «типизированный» значит «именованный», а богатая схема MCP
невыразима). Пятая — `DURABLE_EFFECT` недостижим для инструмента с риском `CONFIRM` и выше — адресована
**A4′**; **пользователя при этом всё равно останавливают** (`RISK_LEVEL` забирает ветку), так что это
пробел точности трассы, а не дыра в безопасности. Без этого предложения находка читается как «необратимые
действия проскакивают мимо согласия», что неправда.

**Вторая находка-расхождение, найденная последней.** `ConsoleHarness.restore()` пишет `SessionPaused`
безусловно, а `LauncherAgentSession.restoreOnStart` имеет против ровно этого явную ветку с записанным
аргументом. Измерено: четыре захода, уходящих от приглашения, — 17 событий на одной сессии. Обе
стороны правы по-своему (перезапуск харнесса **и есть** смерть процесса, старт приложения — нет),
поэтому чинить нечего: движок просто не говорит, что означает `pausedForRestore()` — факт смерти
процесса или факт восстановления. Пока не сказано, каждый потребитель решает сам. → **A4′**.

**§6.3 не «чинить».** Одна и та же реальность — «того, о чём ты просил, нет» — заканчивается `Failed`
на JVM и `Completed` на Android, потому что словарь наблюдений это закрытый двузначный enum, написанный
для лаунчера. Инструкция владельца от 2026-08-23: асимметрия **остаётся**, унификация **не является
задачей**. Держится это двумя гвардами в двух модулях, а не абзацем: диф, трогающий
`CoreVocabularyFreezeGuardTest` или тест `a missing target ends Failed here where Android ends
Completed - INTENDED divergence, owned by A1 prime` ради их согласования, — **откат, а не результат**.

**Рекомендация §11.2 — наблюдение, а не решение.** Шесть контрактов, оказавшихся написанными под
лаунчер (`GoalShape`, `ObservedFact`, `CommandFailure`, `StepRationale`, `ArgType`, `TemplatePlanner`),
— **все закрытые суммы**. Контракт, переживший контакт без единой правки ядра, — `ToolId`, **открытый
value class над `String`**. Второй выживший, `AgentSessionIdFactory`, — не value-тип, а **порт**, и он
показывает второй способ: вынести непортируемое (`UUID`) за границу вместо того, чтобы называть его в
ядре. Измерено: три новых `ToolId` — ноль правок ядра; одно новое значение `GoalShape` — четыре файла
в трёх модулях. **Развилку A1 это не решает**, и обе её ветки остались ровно настолько же дешёвыми,
насколько были.

**Одна мина на будущее, замеченная ревью и не тронутая:** задача `:consumer:jvm:run` держит
`standardInput = System.in` — без этого Gradle отдаёт процессу пустой stdin и согласие набрать
невозможно. Это безопасно **только пока не включён configuration cache** (`org.gradle.configuration-cache`
в `gradle.properties` нет). В день, когда его включат, эта задача упрётся в сериализацию этого поля.
Записано здесь, а не «исправлено» заранее.

### Ловушка Gradle `UP-TO-DATE` — и как её на самом деле проверять

Тест, читающий файлы вне своего source set, Gradle не считает входом задачи: задача остаётся
`UP-TO-DATE`, гвард молча не запускается. A0 закрыл это ещё для двух корней (`inputs.dir` на
`domain/src/commonMain/kotlin`, `data/repository/src/main/java`, `feature/launcher/src/main/java`)
в дополнение к строке матрицы.

**Урок, который дороже самой заплатки:** проверить объявление инпутов можно **только** мутацией с
идентичным байткодом. Наивная мутация (добавить импорт) сдвигает все строки ниже, компилированный
выход `:domain` меняется, задача перезапускается по постороннему поводу — и отчитывается ложным
«ловушка закрыта». Мутация, уравновешенная удалённой пустой строкой, оставила
`:app:testDebugUnitTest` `FROM-CACHE` с кодом 0, пока `domain/agent` импортировал `LauncherAction`;
с восстановленным блоком инпутов та же мутация — RED. Задача **без outputs** (как
`checkOwnerReviewedLocaleStrings`) этой болезнью не страдает: она не бывает `UP-TO-DATE`.

### Протокол, который здесь реально сработал — не сокращать

- **Три предписания контролирующей сессии были НЕВЕРНЫ**, и все три пойманы одинаково: исполнитель
  сначала выполнил буквальную формулировку брифа, снял лог и отклонил её **с доказательством**, а не
  с аргументом. Дважды буквальная версия уехала бы красным гвардом. Брифуйте исполнителя именно так и
  считайте «я счёл это неверным, вот лог» желаемым исходом, а не трением.
- **Заплатка выращивает собственную болезнь на шаг в сторону.** Находка `F2` убрала ассерт, который не
  может упасть; заплатка **для этого класса** вырастила новый такой же (`D10`), причём не копированием
  — он возник потому, что деривация стала фильтровать то, что ассерт раньше проверял. Трижды за блок
  следующая проверка ловила дефект предыдущей. Это аргумент против сокращения цепочки ревью после
  раунда, вернувшегося APPROVE.
- **Зелёный прогон нового гварда по-прежнему не доказывает ничего.** Мутация или это не гвард.
- **Развилка, которой не было в плане, — норма.** F5 Этапа 4.0 и F6 A0 всплыли при чтении, а не при
  написании кода. Правило forks-before-code относится и к ним: спрашивать, не додумывать.
- **Мутации сажать и откатывать в ОДНОМ вызове оболочки** с `trap … EXIT`: агент однажды умер на
  ошибке API, оставив `MutationProbe.kt` в production-исходниках. Восстановились **возобновлением**
  агента с наблюдаемым состоянием дерева, а не перезапуском — свежий агент унаследовал бы чужой зонд.
  Проверять состояние дерева **полным** `git status --porcelain --untracked-files=all`, а не грепом по
  содержимому: в A0.5 один зонд (`ZzProbeTmpTest.kt`) греп пережил, потому что не содержал ни одной
  искомой строки. Имя файла — тоже улика.
- **`git checkout -- <file>` восстанавливает файл ЦЕЛИКОМ** — вместе с легитимной правкой, сделанной в
  том же файле до мутации. В A0.5 так исчезла правка KDoc: дерево чистое, прогон зелёный, находка
  отчитана исправленной, а её в коде нет. Поймано только проверкой, что ожидаемая правка **на месте**
  (`git diff --stat` показал пусто там, где должна была быть правка), а не тем, что мутация ушла.
  Правило: **коммитить легитимную правку до мутации того же файла**; для незакоммиченного файла —
  copy-based ловушка с проверкой бэкапа **до** посадки.
- **Мутация, не севшая, выглядит точно так же, как не убившая.** Проверка посадки утверждала, что
  строка с отступом 8 встречается один раз, — но её же содержало место вызова с отступом 16, счёт дал
  2, ассерт бросил, на диск не записалось **ничего**, и Gradle напечатал `EXIT=0, failures=0`. Без
  утверждения на этапе посадки это записалось бы как «механизм удалён, набор зелёный» — прямо
  противоположное истине. Правило: **утверждать посадку правки до запуска набора.**
- **Сигнатурный дефект, всплывший в A0.5 пять раз:** проза написана от задуманного поведения, ассерт —
  от удобного наблюдаемого, и ничто не заставляет их совпасть. KDoc класса, приписывающий себе свойство
  use case; имя теста «файла больше нет» при ассерте только на `assertNull`; набор про согласие, ни разу
  не проверивший **значение** согласия; тест «второго тапа», не касавшийся CAS, который называл; и
  комментарий сборки, объявивший объявление входа несущим там, где измерение (Ruling P20) говорило
  обратное. Ловила это каждый раз только мутация — или ревьюер, сверивший прозу с измерением.

### Инварианты, которые не ослаблять

- **F6.** `ToolExecutor` принимает **только** `ResolvedInvocation`, а `InvocationValidator.resolve` —
  его единственный конструктор, поэтому несвязанная ссылка **не может скомпилироваться** до внешнего
  мира. `args_json` на диске хранит `ArgSource`, а не значения: переживший процесс план
  пере-связывается с уцелевшими наблюдениями, а не проигрывает значение, замороженное при планировании.
- **Три состояния «понимание недоступно» взаимоисключающи по построению.** `RouteCommandUseCase` —
  цепочка ранних возвратов, не три независимых `if`. Четвёртую причину добавлять **в цепочку на своё
  место по внешности**, иначе свойство сломается молча (закреплено тестом `all three causes at once —
  only the outermost is reported`). Врезка агента стоит **выше** проверки `localOnlyMode` — это
  решение F4, а не случайность порядка.
- **Гейт локалей — подпись над содержимым.** `OWNER-REVIEWED <дата> sha256:<16 hex>` по Class B ключам
  файла. **Дайджест не вписывать самому** — это и есть акт подписи; текст сначала читает владелец.
- **Семь значений `ActionIds` заморожены байт-в-байт** (ADR 3/4). Любое решение развилки A1 обязано это
  уважать. **Саму развилку A1** («параллельный словарь против эволюции `ActionCatalog` на месте») —
  по-прежнему **не решать**: она принадлежит A1′ и решается на спеке, переписанной после ADR 2/4.
  A1′ владеет уровнями инструментов (`DOC-ILM-2`), единой точкой risk → gate (`DOC-ADL-1`) и работой по
  источникам установки (`B2`/`B3`/`B4` §3.6 Master Plan).
- **Направление сведения спеки и кода — вопрос, а не умолчание.** Прецеденты: F6 свели правкой кода
  (Task 5b), `goal_shape_arg` — правкой **спеки** решением владельца, иначе единственное владельческое
  исключение в денилисте `RoomColumnNamesGuardTest` стало бы двумя.

### Долги без блока-владельца — их никто не подберёт сам

- **`RoomColumnNames` — рукописная копия**, и `RoomColumnNamesGuardTest` сканирует **её**, а не
  сущности и не экспортированную схему. Колонка, добавленная в `@Entity` и забытая в инвентаре,
  проходит гвард молча — включая колонку с запрещённым термином в имени. Важнее с A0: Task 10 положил
  в базу первую колонку с **сырым текстом команды** (`agent_session.goal_text`). Сейчас инвентарь и
  схема совпадают (сверено по `schemas/…/4.json`, восемь таблиц). Лечится выводом `BY_TABLE` из
  экспортированной схемы.
- **`FakeToolRegistry.withA0Tools()` — зеркало `SystemIntentToolSource`, ничем к нему не пришитое.**
  `SystemIntentToolContractTest` сверяет source против executor, а не фейк против source, поэтому
  прод может переименовать аргумент или сменить risk, а доменные тесты продолжат пиннить форму,
  которой уже нет. Task 13 это не покрыл; дешевле всего — строка паритета.

### Среда и гейт

- **Ловушка среды, пойманная 2026-08-22.** Открытие проекта в Android Studio генерирует
  `gradle/gradle-daemon-jvm.properties` с `toolchainVersion=25` (дефолтный JDK машины — 25.0.3). Этот
  файл задаёт JVM **демона** Gradle и читается **до** `-Porg.gradle.java.installations.paths`, поэтому
  обычная защита проекта его не покрывает. Файл удалён; вернётся при следующей синхронизации IDE.
  Проверяйте `git status` перед коммитом и чините в источнике: Android Studio → Build Tools → Gradle →
  Gradle JDK → 17.
- **Гейт блока — одна команда:**
  `./gradlew --no-daemon -Porg.gradle.java.installations.paths=/home/Suleiman/jdks/jdk-17.0.19+10 :domain:jvmTest testDebugUnitTest assembleDebug :consumer:jvm:test`.
  `:domain:jvmTest` и `:consumer:jvm:test` перечислять **обязательно**: `testDebugUnitTest` до первого
  **не доходит** после перехода `:domain` на KMP (там живёт весь движок), а до второго не доходит
  вообще. На 2026-08-26 это **1219 тестов, 0 падений** (419 в `:domain:jvmTest`, 56 в `:consumer:jvm`).
  Через `tail` — никогда; числа читать из JUnit XML, а не из консоли. Набор, вернувшийся `UP-TO-DATE`,
  для закрывающего числа перезапускать через `--rerun`: инкрементальность Gradle — вывод, а не
  наблюдение.
- **`:domain` на KMP.** Production — `commonMain/kotlin`, тесты — `jvmTest/kotlin`. `targetSdk` держится
  на 36 (Robolectric не знает API 37), `compileSdk` = 37. AGP 9 built-in-Kotlin / new DSL — **opt-out**,
  не принятие.
- **`CLAUDE.md` — не дайджест.** Текущее состояние + hard rules + указатели; история — в
  `decisions.md`. Историю обратно в `CLAUDE.md` не возвращать.
