# SIDR — переход от умного роутера к агентной системе

> **STATUS: APPROVED (владелец, 2026-08-18).** Стратегический маршрут агентного трека, не план блока.
> Снимает развилки, блокировавшие A1–A6 с 2026-07-11. Этапы 1/0/2/3 исполнимы по этому документу;
> Этапы 4–7 заходят обычным циклом `brainstorm → spec → plan → build`. См. §«Как использовать этот документ».

## Context

**Зачем этот план.** Sidr прошёл Stage 1 (AI-Launcher MVP) и весь дизайн-трек DS-1…DS-11 + I18N-1.
Инженерная база сильная: `:domain` чист (stdlib+coroutines, проверяется каждый блок), приватность
выражена исполняемыми guard-тестами, каждый блок закрывается ADR + приёмкой на устройстве.

Но заявленная цель — агентная ОС — не начата. Собственный ADR от 2026-07-10 постановил «next
architectural slice = A1»; спеки A1–A6 написаны 2026-07-11. За 5,5 недель после этого закрыто шесть
дизайн-блоков и **ноль агентных**; все шесть планов A1–A6 до сих пор `STATUS: PROPOSED`.

Причина структурная: у дизайн-трека есть Master Plan (2087 строк), милстоуны, DoD, change-control —
он всегда «готов к следующему блоку». У агентного трека — шесть спек и четыре нерешённые развилки, он
всегда «требует решения». Трек с бо́льшим процессом выигрывает независимо от важности. Этот план
устраняет эту асимметрию и снимает четыре развилки.

**Что конкретно мешает движку сегодня:**

1. **У агента нет рук.** `DefaultActionCatalog` — 7 действий, 5 из них «открыть что-то у себя».
   Многошаговый план поверх этого даёт «открой приложение → открой приложение».
2. **Понимание заперто за префиксным матчером.** `RuleBasedIntentMatcher` = 7 глаголов
   (`open/launch/start`, `install`, `search/find/google`) + 2 ключа настроек + 7 строк команд.
   Правило «LLM консультируется только при low-confidence» означает, что модель никогда не видит
   задачу целиком. Многошаговые цели структурно не проходят этот фильтр.
3. **Матчер понимает только английский.** Все константы — английские литералы. На устройстве
   владельца (системная локаль `ru-RU`, интерфейс русский) «открой телеграм» → `UnknownIntent`
   confidence 0.10; `llmRouterEnabled` по умолчанию `false` ⇒ **русская команда офлайн не работает
   вообще.** `LocaleCompletenessGuardTest` это не ловит: он проверяет `strings.xml`, а константы
   матчера — hardcoded Kotlin-множества в `:data:repository`.
4. **~1400 строк инертного ONNX** едут в каждом APK. OQ#1/#2 открыты 14 месяцев. Классификатор на
   7 меток не извлекает аргументы (это делает `SlotExtractor` регуляркой) и по построению
   ограничен до подсказки (`NluConfidenceCalibrator` мапит в `[0.50, 0.85)`).
5. **Платформа ушла вперёд.** `AppFunctions`, `MCP`, `Gemini Nano`, `AICore`, `ADK` — ноль
   упоминаний во всей документации.
6. **Цель «ПК» отсутствует в доках**, а решение по портируемости ядра дешевеет только сегодня.

**Ожидаемый результат.** Работающий агентный движок: цель → план → гейт → инструмент → наблюдение →
результат → трассировка, с руками из реестра ОС, портируемым ядром и сохранением всех инвариантов
приватности и согласия.

## Новое правило вместо «rule-first before any LLM call»

Заменяет формулировку в `CLAUDE.md` (Hard rules) и `docs/architecture.md` (Principles):

```
Понимание принадлежит модели. Исполнение принадлежит детерминированному слою.

1. FastPath (детерминированный, локализованный) отвечает на частотные точные команды
   без модели. Это оптимизация задержки, НЕ фильтр понимания.
2. Кэш выученных планов воспроизводит уже понятые формы целей детерминированно и офлайн.
3. Всё остальное идёт к планировщику-модели. Промах FastPath больше НЕ является
   основанием ответить «Unknown command».
4. Ничто из предложенного моделью не исполняется, не получает прав и не покидает
   устройство иначе как через детерминированные ворота:
   ToolRegistry → валидация аргументов → preconditions → риск-гейт/consent →
   границы цикла → egress allow-list → трассировка.
5. Router-off / offline / no-key ⇒ FastPath + кэш планов + честное «нужна сеть».
   Байт-в-байт паритет rule-only остаётся проверяемым тестом.
```

**Следствие, требующее решения внутри Этапа 1:** `FeatureFlags.llmRouterEnabled` (сейчас `false`)
перестаёт быть воротами понимания. Рекомендация — понимание доступно, когда сконфигурирован
провайдер; явный переключатель «только локально» сохраняется для пользователей, которым он нужен.

## Правило роста: функционал масштабируется, границы — нет

Замысел владельца — наращивать функционал по мере роста потребностей, не фиксируя облик системы
заранее. Это принимается и распространяется на поверхность (UI появляется вслед за способностью) и
на абстракции (обобщать при появлении второго потребителя, а не в предвкушении — существующий
принцип feature-first).

Из этого правила **исключаются границы**. Реестр как единственный путь к миру, валидация аргументов,
гейт согласия, лимиты цикла, трассировка, egress allow-list и откат закладываются на **первом же
срезе, для двух инструментов** — не «когда понадобится». Причина механическая: если рантайм сначала
научился вызывать 20 инструментов, а согласие добавляется потом, это 20 мест, где его можно забыть.
Если согласие живёт внутри `ToolExecutor` с первого дня, инструмент №21 получает его бесплатно.
Та же логика, по которой guard-тесты приватности в этом проекте написаны до того, как появилось что
утекать.

## Как использовать этот документ

Это **не** план блока в смысле репозитория (`docs/superpowers/plans/*.md` = пронумерованные задачи с
файлами и тестами, по которым идёт сессия). Он стоит **выше спек**: снимает развилки, блокировавшие
агентный трек с 2026-07-11, и задаёт очередь блоков.

```
CLAUDE.md → decisions.md (ADR) → specs/*.md → plans/*.md (Task 1..N) → сессия → гейт + ADR
                    ▲
            этот документ решает, ЧТО и в каком порядке сюда попадает
```

| Этап | Исполним по этому документу? |
|---|---|
| 1 (стратегические ADR), 0 (расчистка), 2 (тулчейн + KMP), 3 (агентный Master Plan) | **Да** — файлы и содержание определены |
| **4.0 (инверсия флага понимания)** | **Да** — радиус и файлы определены; четыре развилки спрашиваются у владельца в начале сессии |
| 4–7 (A0, A1′, A4′, A2/A3, A5/A6) | **Нет** — каждому нужна своя спека и свой план с задачами, обычным циклом `brainstorm → spec → plan → build` |

Кикофф сессии (по образцу `ai-launcher-mvp-plan.md` §0):

```
Работаем над Этапом <N> из docs/superpowers/plans/<этот-файл>.md.
Прочитай CLAUDE.md (Hard rules) и §«Решения владельца» + раздел нужного этапа.
Этап закрывается зелёными testDebugUnitTest + assembleDebug, записью ADR
и синхронизацией CLAUDE.md / current-status.md.
```

**Порядок: Этап 1 идёт первым.** Стратегические решения фиксируются до кода — прецедент AIL-4, где
блокирующий ADR писался перед реализацией. В частности 0.3 (удаление 1400 строк ONNX) исполняет
решение ADR №2; без него это было бы оправдание задним числом.

### Почему коммит, а не «оставлю в дереве»

Гранулярность — **не сессия, а наименьшее самосогласованное состояние**. В I18N-1 это дало ~28
коммитов за 8 дней при 16 задачах; иногда 4–5 за сессию, иногда ноль (аналитической сессии коммитить
нечего).

Коммит в агентной работе покупает три вещи:

1. **Восстановление.** 2026-08-18 в этом репозитории: незакоммиченный черновик плана был перезаписан
   и потерян навсегда; `LocaleCompletenessGuardTest` (+96 строк) в том же дереве уцелел, потому что
   был закоммичен (`bce726c`). Одинаковый риск, разный исход — разница только в коммите.
2. **Поверхность ревью.** `.superpowers/sdd/` состоит из `review-<sha>..<sha>.diff` — ревьюер-агент
   смотрит диff между коммитами. Нет коммитов — нет ревью.
3. **Передача контекста.** `git log --oneline -5` — самый дешёвый handoff. Поэтому качество
   сообщений (conventional commits + скоуп блока) не церемония, а рабочий канал.

**Не коммитить:** при красном гейте (чинить или парковать на scratch-ветке) и при выбрасываемой
разведке.

**Экспозиция:** ветка `launcher--7` на 2026-08-19 была на 38+ коммитов впереди `codeberg/launcher--7`
и не запушена. Пуш — решение владельца, но пока его нет, локальный git остаётся единственной копией.

### Subagent-driven (SDD)

Применять на Этапах 4–7, когда у блока появится план с пронумерованными независимыми
задачами — как I18N-1 (16 задач) и DS-6B (12). Не применять на Этапах 0–3: задачи там
связанные, а два форка Этапа 1 требуют владельца, которого субагент спросить не может.

### Механика SDD-блока — правила, оплаченные A0, A0.5 и A1′

Раздел выше говорит, **когда** применять SDD; этот — **как его вести, чтобы блок не соврал о себе**.
Каждое правило оплачено конкретным случаем в этом репозитории; правило без случая сюда не пишется.
Живёт здесь, а не в §HANDOFF, потому что §HANDOFF переписывается каждой закрывающейся сессией, а эти
правила верны и через пять блоков.

**Леджер блока — расходник; урок из него — нет.** `.superpowers/sdd/<блок>/progress.md` игнорируется
git'ом (`.superpowers/sdd/.gitignore` = `*`): он не в истории, не в бэкапе, умирает от
`git clean -fdx`. Всё долговечное вынимается **до** закрытия блока: рулинги и мутационная таблица →
ADR, адреса следующему блоку → §HANDOFF, долг → `CLAUDE.md`, процессное правило → сюда. A1′ закрылся
с ADR и §HANDOFF, но процессная часть его леджера в репозиторий не попала и извлекалась отдельным
проходом уже после закрытия.

**Смерть субагента mid-task — штатное событие, и протокол восстановления один.** В A1′ их было не
меньше четырёх (задачи 3, 7, 9 и раунд правок задачи 10), плюс прогон финального ревью, который
отгрузил `356fe1a` и остановился, не написав отчёта; §HANDOFF A0.5 записал ещё одну (ревьюер ADR).

- **Первым действием — полный `git status --porcelain --untracked-files=all`**, не греп по
  содержимому. Он отличает «работа в дереве, не закоммичена» от «работа потеряна». За весь трек
  второго не случилось ни разу — но узнаётся это только полным статусом.
- **HEAD, названный в диспатче, — утверждение, а не факт: `git log --oneline -3` до первой правки.**
  Умерший агент мог успеть закоммитить. Диспатч финального ревью A1′ говорил «HEAD `753e75a`, дерево
  чисто»; реально HEAD был уже `356fe1a` — полная реализация всех пяти находок. Принято на веру, это
  дало бы повторную реализацию пяти находок поверх самих себя.

**Мутационный протокол.** Он и есть причина, по которой числа блока чего-то стоят.

- **Коммит легитимной правки — ДО мутации того же файла.** `git checkout -- <file>` восстанавливает
  файл целиком, вместе с правкой. Урок A0.5; в A1′ повторился с обеих сторон: задача 3 была
  закоммичена до мутационного раунда именно поэтому, а имплементатор задачи 10 всё-таки выкинул
  `git checkout`'ом собственные новые тесты вместе с мутацией и поймал это только `git status`'ом.
- **Восстановление мутации — `trap … EXIT` + `git checkout --`, никогда `cp`.** Раунд 2 задачи 11
  начался с грязного дерева: `cp`-восстановление в самопроверке имплементатора отрапортовало
  «`git diff HEAD` чисто», хотя это было не так.
- **Самопроверка автора над собственной правкой — не доказательство.** Отдельное место
  `mutation-prover` дважды нашло настоящий дефект в том, что автор объявил закрытым: гварды
  `ToolVocabularyLocaleGuardTest`/`ToolVocabularyReachabilityTest` были зелёными на **пустой**
  таблице, а в `DoctrineGuardTest` ассерт «no two registered tools share an id» был
  **нефальсифицируем** — `ToolFederation` резолвит коллизию до `.all()`, так что дубликат не доезжал
  до проверки (это spec success criterion 3 блока, не выполненный на первом проходе). Оба нашлись
  только потому, что мутации ставил не автор.
- **Новый гвард идёт к `mutation-prover`; зелёный прогон не доказывает ничего.** Добавление записи в
  уже доказанный гвард — не идёт: оно доказывает себя единственным способом, которым может провалиться
  (создать файл до записи в списке → наблюдаемый RED). Это Ruling R12 A1′.
- **Мутационный раунд кончается чистым перепрогоном ДО коммита** (Ruling R16). Иначе XML на диске
  противоречит телу коммита: `17f3401` нёс «девять RED», а на диске лежал красный отставший
  фильтрованный прогон. Утверждение оказалось верным — но проверил это ревьюер, а не процесс.
- **Раунд с пустым дифом на повторное ревью не идёт** (Ruling R10): второй паре глаз нечего читать,
  контроллер проверяет артефакт сам (mtime XML, `git status --porcelain` на нужном коммите).

**Диспатч — тоже код, и в нём тоже бывают ложные утверждения.**

- **Бриф, который говорит «создать файл X», сверяется с деревом до отправки.** В задаче 12
  `SystemIntentToolContractTest.kt` уже существовал, и первым движением имплементатора был `Write`
  поверх него; он поймал это сам и восстановил `git checkout --`. Ошибка была диспатча: контроллер
  перенёс слово «create» из плана, не посмотрев в дерево.
- **Имплементатору говорится прямо: Gradle — на переднем плане.** Первый ход задачи 5 кончился
  ожиданием фонового прогона, который никто не опросил; конец хода субагента — не ожидание.
- **Контроллер ошибается так же, как имплементатор, и ловится местом ниже.** Ruling R14 утверждал,
  что голый `lowercase()` возвращает турецкий баг с точечной `i`; имплементатор опроверг это мутацией
  (`String.lowercase()` — `Locale.ROOT` с Kotlin 1.5). Половина рулинга устояла, половина была
  неверна, и опровержение записано в леджер, а не тихо исправлено. Ревьюер задачи 3 поймал Critical,
  которую контроллер пропустил. Отсюда: **ревьюерское место не удешевлять.**
- **Проза, называющая тест, символ или инвариант, — проверяемое утверждение, и проверяется по
  дереву.** Этот класс стоил A1′ нескольких раундов правок: «`domain/tool` не имеет импортного ребра
  в `domain/action`» (ложно, стояло в трёх местах, автор нашёл в самопроверке и отгрузил всё равно),
  «verbatim» про аргумент после перехода на `CommandNormalizer`, KDoc, называвший тест через тире там,
  где в имени теста дефис, — то есть тест, которого нет. Компилятор такие предложения не ловит.
- **Вперёд-ссылка, предписанная планом, — долг, а не мелочь.** KDoc, называющий гвард, которого ещё
  нет (задачи 2 и 4 A1′), закрывает та задача, которая гвард создаёт, — и она перечитывает **все**
  такие предложения, а не только пишет гвард.

**Числа — только из прогона, напечатавшего `N actionable tasks: N executed`, и только из JUnit XML;
`--rerun-tasks`, никогда `--rerun`** (Ruling R9: `--rerun` дал `BUILD SUCCESSFUL` за 11 секунд при
нуле исполненных тестовых задач). Полная команда гейта — §«Среда и гейт» в HANDOFF.

**Как этот протокол влияет на нарезку задач.** Самая дорогая находка A1′ — не процессная: четыре
слоя, каждый полностью протестирован изолированно, в сумме дали мёртвую способность, и все тесты были
зелёные. Полный разбор — в ADR «2026-09-03 — Этап 5 (A1′)» и в §HANDOFF; следствие для плана блока:
если блок создаёт новый шов между слоями, **какая-то задача обязана нести тест, пересекающий этот
шов**, иначе набор зелёных задач ничего не говорит о продукте.

### 3.2. Извлечение доктринальной матрицы

**Проблема.** Восемь исламских принципов (Niyyah · Amanah · Mizan · Ilm · Adl · Haya · Sukun ·

**дизайн-трека**. Но половина строк матрицы §5 указывает на инженерные слои: Niyyah → A4,
Ilm → A4–A5, Adl → A1/A4/A6, Human authority → A4/A6. Агент, работающий над рантаймом, не имеет
причин открывать «Design System Master Plan». Категориальная ошибка, которая станет дорогой ровно
тогда, когда появится второй трек.

**Почему именно на Этапе 3, а не раньше.** До агентного Master Plan у доктрины **один** потребитель,
и извлекать общее незачем. После — два, и документ перестаёт принадлежать одному из треков. Та же
логика, что «Framework = ядро с двумя потребителями» и что правило A2/A3 «строить по потребителю».

**Что извлекать — операционную часть, не философию:**

| Остаётся в Master Plan | Переезжает |
|---|---|
| §4 — восемь принципов прозой (философия) | §5 Traceability Matrix |
| | §5.1 приоритет при конфликте |
| | §5.2 verification vocabulary |
| | §20.1 calm budgets |

Это разделение принципиально, а не косметическое. Аудит §21 записал **Риск 5 — «исламская эстетика
станет декоративной»**. Отдельный документ с принципами прозой читается как манифест и тянет в
декоративную сторону; отдельный документ-таблица с типами проверок и именами тестов читается как
инженерное ограничение. Один материал, разный жанр, разная судьба.

**Форма — четыре колонки вместо нынешних пяти прозаических:**

```
ID          правило                               тип проверки   чем обеспечено
DOC-AML-1   egress только через allow-list        arch-guard     AiRequestGuardTest
DOC-ADL-1   одинаковый risk → одинаковый gate     unit           <нет> ← долг A1′
DOC-SKN-1   idle animation budget = 0             screenshot     <goldens>
DOC-ILM-2   EXTERNAL-инструмент несёт provenance  arch-guard     <нет> ← долг A1′
DOC-NYH-1   шаг с неоднозначным аргументом
            уточняет, а не догадывается           unit           <нет> ← долг A4′
```

Три вещи, которых сейчас нет и которые всё меняют:

1. **Стабильный ID** — ADR и тест ссылаются на правило, а не пересказывают его. Пересказ есть
   механизм расхождения документов (прецедент: три конфликта v1↔v1.1, разбиравшиеся в DS-0).
2. **Тип из закрытого словаря §5.2, проставленный в самой таблице.** Сейчас словарь определён

   в колонке проза.
3. **Колонка «чем обеспечено»** — имя файла теста либо честное `<нет>`. Превращает документ из
   декларации в **список долгов**: пустая ячейка видна сразу.

**Что делает его системным, а не девятым документом:** guard-the-guard, уже изобретённый в этом
репозитории (`module_prefixes_cover_every_module_that_ships_strings`,
`scoped_roots_cover_every_ui_module`). Тест читает эту таблицу и краснеет, если правило заявляет
`arch-guard`, а такого теста в репозитории нет. Документ перестаёт стареть незаметно.

**Попутно чинится филинг** (дёшево сделать заодно):
- Master Plan лежит в `docs/design/`, объявленной ADR «DS-0» архивом (*«archive of inputs, not the

### Исходное задание этапа (для истории)

**Первый вертикальный срез. Цель — доказать движок, а не построить слои.**

Одна реальная двухшаговая цель проходит `goal → plan → gate → tool → observe → tool → result → trace`
и принимается на устройстве. Минимальные куски A1/A2/A4; **без** A3/A5/A6, без DAG, без переплана.

Новое в `:domain` (портируемое ядро):
- `domain/tool/` — `ToolId`, `ToolDescriptor`, `ToolInvocation`, `ToolResult`, `ToolRegistry`,

- `domain/agent/` — `AgentGoal`, `ExecutionPlan`, `PlanStep`, `Planner` (порт), `AgentExecutor`,
  `AgentSession`, `ExecutionState`, `RuntimeBudget`, `ConsentCheckpoint`

- `ProposalValidator` (`domain/ai/router/`) — образец fail-closed валидации аргументов
- `ExecuteActionUseCase` → `IntentActionResolver` → `ActionExecutor` — становится
  `SYSTEM_INTENT`-уровнем `ToolExecutor`
- `ActionRiskLevel` + `SidrActionGate` (`core/ui`) — гейт согласия
- `OutboundContextPolicy` — граница выхода агента
- `OperationResult` — fail-closed везде

UI: минимальная поверхность выполнения на существующих примитивах DS-5
(`SidrActionProposal`, `SidrResultSurface`, `SidrErrorSurface`, `SidrProvenanceLine`,
`SidrActionGate`). Ничего нового в `core/ui` не создавать.

**Поверхность — функция состояния, а не макета.** Один компонент на состояние рантайма; композиция
собирается из того, что сессия реально сообщила. Тогда план на 2 шага и план на 7 шагов, появление
`Blocked` или переход в `AwaitingConsent` не требуют редизайна — облик масштабируется сам.
Нарисованный Execution Stream (аудит §12.4: линейный список из трёх шагов) — **вход, а не спека**:
он не выражает переменное число шагов, замену шага при переплане, согласие как прерывание шага,
неравные длительности, DAG-план и девять состояний сессии. Прецедент — DS-10, где устаревшая
премисса собственной спеки уступила реальности.

## Этап 6 — A4′ Рантайм полностью

### Модель исполнения: лаунчер — процесс, агент — сессия

Не разобрано ни в одной из шести спек, при этом определяет форму продукта. Специфичная для Android
ловушка: **собственное действие агента выбрасывает пользователя из процесса, где агент живёт.**

```
Шаг 1: открыть Календарь → пользователь в Календаре → лаунчер в фоне → процесс может быть убит
Шаг 2: ...                 кто исполняет?
```

Для обычного лаунчера это норма — он своё отработал. Для агента это ломает цикл в **типичном**, а не
краевом случае.

**Ответ — четыре слоя:**

1. **Корректность (обязательна, от процесса не зависит).** `AgentSession` сохраняется после каждого
   перехода состояния. Смерть процесса = прерывание того же класса, что ожидание согласия → `Paused`.
   При возврате пользователя сессия восстанавливается и предлагает продолжить. Возобновление
   идемпотентно. Механика уже требуется спекой A4 («persisted, inspectable state machine»,
   «duplicate resume/confirm cannot execute a step twice») — теперь ясно, зачем.
2. **Удобство (пока процесс жив).** Цикл крутится в существующем `@ApplicationScope`
   (инжектится в `SidrLauncherApp`). Переживает уничтожение Activity, поворот, уход в фон без
   убийства. Обычный случай, без церемоний.
3. **Непрерывность (только когда шаг обязан продолжаться, пока человек в другом приложении).**
   Foreground service с обязательным уведомлением — единственный честный механизм в Android, и он
   совпадает с доктриной: видно, что работает, можно остановить. `android-limitations.md` разрешает
   ровно этот случай («justified and user-visible»).
4. **Никогда.** Фоновые автономные циклы без видимости — уже в non-goals спеки A4, оставить.

**Отдельный процесс агенту не нужен.** Рантайм — машина состояний и несколько объектов, это байты;
единственное тяжёлое в системе (модель) по построению вне процесса (облако либо AICore).
`android:process=":agent"` добавил бы IPC, второй граф Hilt и вторую точку отказа ради экономии байтов.

### Три спеки, которых нет ни в одном документе

1. **Откат и компенсация.** A4 упоминает `PartiallyCompleted` как состояние — и всё. «Шаг 3 из 5
   упал, шаги 1–2 уже изменили мир» не заспецифицировано нигде. Дизайн-док про это говорит
   («Aftermath / undo surface»), домен молчит.
2. **Протокол уточнения.** `PlanResult.Clarify(question)` — терминальный лист. Многоходового
   «агент спросил → человек ответил → план уточнён → продолжили» нет ни в одном контракте.
3. **Кэш выученных планов** — механизм локальности из решения #2. Обобщает
   `ResolutionPreferenceStore` (S2-1) и `AliasStore` (S2-2) с одного действия до плана: цель понята
   моделью один раз → сохраняется шаблон плана (не формулировка) → воспроизводится детерминированно,
   офлайн, на любом железе. Многоязычно бесплатно: шаблон привязан к плану, формулировки
   накапливаются вокруг.

## Этап 7 — A2 / A3 по потребителю, затем A5 / A6

**Спеки A2 и A3 остаются целиком — они написаны верно.** Потребитель у них назван и существует по
замыслу: это `Planner` из спеки A4 (`plan(goal, ContextSnapshot, ToolRegistry, UserMemory)`).
`agentic-os-architecture.md` прямо определяет себя как «direction, not a committed plan» — описывать
целевую форму целиком и есть работа архитектурной спеки, иначе A1 примет решения, блокирующие A2.

Риск не в том, что форма описана, а в том, что спека потом читается как **список к постройке**.
В репозитории есть оба исхода:

| Прецедент | Что сделали | Результат |
|---|---|---|
| **AIL-1** | «ships only the contract + the family vocabulary; the concrete catalog + impl is deferred to AIL-2» | Потребитель пришёл через день, всё сошлось |
| **`:data:ai-local`** | Построено полностью (`ModelStore`, `ModelProvisioner`, `Sha256Verifier`, `KtorModelDownloader`, `ModelDownloadWorker`, `Scheduler`) против `ModelDownloadConfig.INTENT_NLU_PENDING` | Потребитель не пришёл за 14 месяцев; 1400 строк и AAR в каждом APK — удаляются в 0.3 |

Разница не в качестве спеки, а в том, что решил план.

**Правило для A2/A3:** словарь и контракты — целиком (паттерн AIL-1); реализуется только то, что
читает первый планировщик A4; непостроенное помечается в спеке как «спроектировано, не построено,
триггер постройки — <какой>».

### Обязательное проектное решение A2: двойная проекция контекста

Принимается **при проектировании A2, не после** — задним числом это переделка всего слоя контекста,
сейчас стоит почти ничего.

```
ContextEngine
  ├── projectForCloud(snapshot) → узкая, редуцированная, под OutboundContextPolicy
  └── projectForLocal(snapshot) → широкая: сырые данные, НИКОГДА не покидающие устройство
```

**Почему это не преждевременная абстракция, а следствие уже принятых решений.**
`OutboundContextPolicy.ALLOWED` содержит ровно четыре значения — `USER_COMMAND`,
`STATIC_SYSTEM_PROMPT`, `GENERATION_LIMITS`, `ACTION_CATALOG_SCHEMA`. Это значит, что **облачный
планировщик планирует вслепую**: он не видит календарь, местоположение, список приложений и память.
То есть приватностная архитектура проекта — работающая и правильная — **структурно ограничивает
потолок полезности облачного планировщика**, потому что именно эти данные делают агента личным
(«найди свободный вечер», «успею ли до магриба», «открой то, чем я обычно пользуюсь сейчас»).

Спека A2 эту напряжённость чувствует и предлагает компромисс — расширить allow-list на
*редуцированные* поля снимка. Локальной модели компромисс не нужен: ей можно отдать сырой календарь
целиком, потому что ничего не уходит с устройства. **Это и есть настоящая причина, по которой
серьёзной агентной системе нужен локальный вывод — не офлайн и не цена, а доступ к личному
контексту.**

Следствия:
- проекции две с первого дня, даже пока локального планировщика нет — тогда он подключается, а не
  требует переделки;
- `projectForLocal` по построению никогда не проходит через egress-слой; guard-тест обязан это
  доказывать (кандидат в `DOC-AML-*` доктринальной матрицы);
- порт `Planner` (`TemplatePlanner → LocalPlanner → LlmPlanner` в спеке A4) уже резервирует место —
  задача A2 в том, чтобы контекст был готов его наполнить.

Локальный планировщик записывается как **назначенный уровень с зарезервированным швом**, а не как
«ускоритель, может быть, когда-нибудь». Второе при реализации игнорируют.

**Почему здесь цена лишнего поля выше обычной.** Каждое поле `ContextSnapshot` обязано пройти
классификацию в `OutboundContextPolicy`, получить guard-тест против утечки сырых данных, быть
permission-gated и fault-isolated отдельно, и пережить приватностное ревью в каждом последующем
блоке. Неиспользуемое поле здесь — не мёртвый код, а постоянное обязательство в самом чувствительном
слое. То же с A3: `MemoryConflict`/`MemoryMutation` подразумевают политику разрешения конфликтов,
которую до появления конфликтующего писателя пришлось бы писать против воображаемых случаев.

Переиспользовать: существующие `SuggestionProvider`-ы уже fault-isolated и permission-gated —
готовые провайдеры контекста; `ResolutionPreferenceStore` (S2-1) и `AliasStore` (S2-2) — два

A5/A6 — только после того, как A4 выдаёт реальные трассы.

### PREVIEW-поверхности — остаются (решение владельца, 2026-08-18)

Пять `PREVIEW`-вкладок (Tasks / Agents / Activity / Terminal / Interaction Moments) **не удаляются**.
Бейдж `PREVIEW` — это в точности мера, предписанная аудитом (§21, Риск 4: «roadmap должен пометить
их `AVAILABLE NOW` / `FOUNDATION` / `FUTURE CONTRACT`»), поэтому golden rule не нарушен. Слоты в
таб-баре резервируют место и заранее учат пользователя форме — когда A4 приедет, вкладка не
появляется внезапно.

Снимается не сама поверхность, а налог на сопровождение — сейчас решение о превью принимается заново
в каждом сквозном блоке (DS-11 — проверка cmap ради маркера `•`; I18N-1 — отдельное owner-решение об
исключении из локализации; дальше по очереди a11y, темы, матрица goldens, fontScale):

1. **Политика, записанная один раз:** PREVIEW-поверхности по умолчанию исключены из сквозной работы
   (i18n, a11y, goldens, темы). Вопрос перестаёт задаваться в каждом блоке.
2. **Срок годности у каждой вкладки:** `tasks` / `agents` → реальны в A4, `activity` → в A5,
   `terminal` / `interaction moments` → назвать блок или пометить бессрочным демо. Иначе превью
   незаметно становится постоянной мебелью.
3. **Устранить расхождение в доках:** DS-0 фиксирует «target IA = 4 поверхности, 5-табовая навигация
   отложена до A4», а шипнутый `SidrTabBar` уже имеет пять вкладок (`home/apps/tasks/agents/activity`).
   Обновить DS-0 под фактическую IA либо явно записать три слота как резерв.
4. **Оговорка на A4:** когда движок приедет, поверхность определяет он, а не нарисованный макет.

### КРИТИЧЕСКАЯ находка — тот же урок A0 нашёл, другая форма, дороже всех остальных находок блока

Найдена ревьюером задачи 10, принадлежала задаче 9, не была закреплена ни за одной задачей плана.
`AgentSessionMappers.toSessionEntity` **бросал исключение** на `GoalShape.Free` — корректно, когда
писалось (планировщик A0 никогда не производил `Free`); задача 9 изменила эту предпосылку, скомпоновав

`Free`-цель → план найден → `store.save` бросает → заворачивается в `Failure` →
`RouteCommandUseCase:147-150`'s существующая fail-open ветка (см. ниже) молча пропускает → падение в
модельный путь. **Ни сессии, ни таймера, ни ошибки, и все 1285 тестов на тот момент зелёные** — потому
что каждый слой был протестирован изолированно. Исправлено (`1c4a61e`), схема не менялась

пересекает ни один тест, этот путь не проверен — четыре слоя, каждый полностью протестирован
изолированно, в сумме дали мёртвую способность.**

**Класс, из которого это один экземпляр, не тронут.** `RouteCommandUseCase:147-150` по-прежнему молча
падает в модельный путь на **любом** не-`Success` от `AgentSessionStore` — переполнение диска, битая
строка, любой будущий сбой стора. Этот блок нашёл и починил один случай; сам класс — за **A4′**.
**И шаг 2b изменил цену этого класса:** ветка (2) срабатывает, только когда FastPath решил, поэтому её
проваливание возвращает FastPath-ответ и с устройства не уходит ничего; 2b срабатывает на
`isUndecided()`, поэтому то же проваливание отправляет **сырой текст команды в облачную модель** на
цели, которую зарегистрированный инструмент уже опознал детерминированно. Детерминированный слой
обходится ошибкой диска — молча, без сессии, без трейса.

### ЧИТАТЬ ПЕРЕД ТЕМ, КАК ПИСАТЬ АДАПТЕР №3: воркер, который бросит, убьёт лаунчер

Финальное ревью ветки нашло КРИТИЧЕСКУЮ (`356fe1a`): `ContextIntentLauncher.launch` звал
`context.startActivity` голым, и **над ним не ловит никто** — у единственной точки вызова
`AgentExecutor.perform` (`toolExecutor.invoke`) нет `try`, у `RunAgentSessionUseCase.run` тоже, а
`LauncherAgentSession` живёт на `viewModelScope` без `CoroutineExceptionHandler`. На устройстве без
активности для `AlarmClock.ACTION_SET_TIMER` типизированная команда таймера собирала одношаговый
`SAFE`-план — гейт согласия такой не останавливает — и убивала процесс домашнего экрана. Починено
**внутри `Tier0IntentToolWorker`**, и это размещение подтверждено пере-ревью: воркер — последний
слой, ещё способный выдать корректный типизированный результат, а лончер, возвращающий `Unit`,
отчитался бы об успехе для эффекта, которого не было.

**Остаток, и он адресован именно A1″: сдерживание — по-воркерное.** «Вызов инструмента всегда даёт
`ToolResult`» — контракт `ToolWorker`, но держится он соглашением и тремя реализациями, а не
механизмом. Сегодня он не нарушен ни разу — `Tier0IntentToolWorker` ловит две названные ошибки
(набор `AndroidActionExecutor`'s), `SystemIntentToolWorker` наследует сдерживание от неизменной
цепочки `ExecuteActionUseCase → IntentActionResolver → ActionExecutor`, `SandboxToolWorker` ловит
широко (`catch (e: Exception)`, `CancellationException` проброшен). Три сети, ни одна не является
требованием. `ToolWorkerCallSiteGuardTest` и `ToolExecutorCallSiteGuardTest` этого не поймают: они
держат, **откуда** зовут, а не **что** вылетает обратно. Это дыра в механике, а не живой краш.

**Разделение адресов, аргумент целиком — в ADR A1′, раздел «Остаточные ограничения».** Починка —
**A4′**: `try` на единственной точке вызова (или сдерживающая обёртка в `ToolFederation`), где
пойманный бросок становится честным `Failed`, а не выдуманным `Effected`, — там же, где уже лежат
бюджет по стенным часам, staleness и класс fail-open. Обязательство до неё — **A1″**, потому что он
идёт **раньше** A4′ и добавляет ~10 Tier-0-интентов плюс `LauncherApps`/ярлыки, то есть новых
воркеров: A1″ либо закрывает контракт механически, либо пишет в своей спеке, что каждый новый воркер
ловит сам и на каком наборе ошибок. Молчание здесь стоит краша домашнего экрана.

### ЧИТАТЬ ТАМ ЖЕ: гвард на permission видит НЕ всё — два измеренных предела

Первый прогон владельцем Части A приёмочного чеклиста (2026-09-05) нашёл headline-инструмент блока
мёртвым: `AlarmClock.ACTION_SET_TIMER` требует `com.android.alarm.permission.SET_ALARM`, манифест его
не объявлял, `ActivityTaskManager` отказывал каждому вызову — при том что восемь документов
утверждали «ноль новых permission». `939d1d7` объявил permission, исправил все восемь и добавил
`ToolPermissionManifestGuardTest` (`:app`), чтобы этот класс не повторился молча. **Приёмка этим не
пройдена: блок остаётся `CODE-GREEN`**, фикс крутился на телефоне только под агентом, а это словарь
статусов проекта приёмкой не считает.

Независимый мутационный раунд гвард **измерил**, и основные направления он держит: снятое объявление
в манифесте и неотображённое новое действие — оба RED с называнием недостающего; легитимный **полный**
рост — GREEN, над-пиннинга нет; на пустом скане 3 из 4 тестов всё ещё стреляют; рукописная колонка
`requiredPermissions` слаба ровно настолько, насколько объявлена, и не сильнее — переписать её в
«`ACTION_SET_TIMER` не требует ничего» оставляет все четыре теста зелёными, а приложение — в
дофиксовом сломанном состоянии. Отдельной парой подтверждено, что декларация манифеста как `Test`-входа
в `app/build.gradle.kts` держит: без неё та же мутация возвращает `UP-TO-DATE` при exit 0 с живым
дефектом, с ней — RED.

**Тот же раунд измерил два предела, и адресованы они автору адаптера №3, то есть A1″:**

1. **`Intent(…)`, переехавший на один файл вбок, невидим гварду целиком.** Все его утверждения
   стартуют от набора файлов, в который файл попадает, только если он **и** объявляет `ToolWorker`,
   **и** сам содержит `Intent(`. Воркер, делегирующий сборку интента обычному объекту-хелперу, выдаёт
   интенты, которых гвард не читает никогда; пин покрытия не спасает — хелпер не `ToolWorker`, значит
   и в сканируемое множество не входит. Измерено инструментом `call_number`, чей воркер зовёт хелпер,
   собирающий `Intent.ACTION_CALL`, при отсутствующем в манифесте `android.permission.CALL_PHONE`:
   **зелено 4/4** — ровно та форма дефекта, ради которой гвард написан, в одном рефакторинге от него.
   Это важно буквально здесь: всё содержание A1″ — новые Tier-0-интенты, а общий хелпер сборки
   интентов ровно то, что естественно написать, добавляя их десяток.
2. **Гвард ключуется на воркерах, а не на зарегистрированных инструментах.** Тотальность срабатывает
   на `Intent(` в файле воркера, а не на `ToolDescriptor`, который объявляет `ToolRegistry`, — поэтому
   инструмент, зарегистрированный в источнике без соответствующей ветки воркера, невидим всем
   утверждениям гварда. Вопрос, на который класс отвечает на самом деле, — «у каждого ли интента,
   выпускаемого **сканируемым воркером**, объявлен permission», а не «может ли вообще запуститься
   каждый зарегистрированный инструмент». Дефект 2026-09-05 был экземпляром именно второго вопроса.

**Ни один из двух не является живым дефектом сегодня** — оба отгруженных воркера строят интенты инлайн,
манифест корректен. Это пределы того, что гвард **видит**, и записаны они потому, что рискует ими
следующий автор, а не этот. Закрытие любого из двух — ключевание скана на том, что объявляет реестр, а
не на файлах воркеров: **другой гвард, а не более широкая регулярка**. Полная формулировка — в KDoc
самого теста (`app/src/test/java/com/sidr/launcher/agent/ToolPermissionManifestGuardTest.kt`);
указатель — в `CLAUDE.md`, Known debt.

### Ловушка Gradle `UP-TO-DATE` — и как её на самом деле проверять

Тест, читающий файлы вне своего source set, Gradle не считает входом задачи: задача остаётся
`UP-TO-DATE`, гвард молча не запускается. A0 закрыл это для трёх корней (`inputs.dir` на
`domain/src/commonMain/kotlin`, `data/repository/src/main/java`, `feature/launcher/src/main/java`) в
дополнение к строке матрицы; A1′ добавил пятый сканируемый корень (`consumer/jvm/src/main/kotlin`) и
подтвердил все пять объявлены как Gradle-инпуты (задача 3), не полагаясь на то, что они уже были.

**Второй, отдельный вариант той же ловушки — сама команда `--rerun` vs. `--rerun-tasks` (Ruling R9
выше).** Инкрементальность Gradle возвращает `UP-TO-DATE` молча и всё равно печатает
`BUILD SUCCESSFUL`; единственная защита — `N actionable tasks: N executed` в выводе, проверенная на
каждое закрывающее число, а не доверие к коду выхода.

**Урок, который дороже самой заплатки (A0):** проверить объявление инпутов можно **только** мутацией с
идентичным байткодом — наивная мутация (добавить импорт) сдвигает строки и меняет компилированный
выход по постороннему поводу. Задача без outputs (как `checkOwnerReviewedLocaleStrings`) этой болезнью
не страдает — она не бывает `UP-TO-DATE`.

### Инварианты, которые не ослаблять

- **F6, исправлено (спека §3.6 A1′; старая формулировка этого раздела была false as written).**
  `ToolExecutor` принимает **только** `ResolvedInvocation`, и `InvocationValidator.resolve` — его
  единственный конструктор, поэтому несвязанная ссылка не может скомпилироваться до внешнего мира. Но
  **`args_json` на диске ДЕЙСТВИТЕЛЬНО хранит значение**: `AgentSessionMappers.kt:218` кодирует
  `ArgSource.Literal` **со значением**. Верно по замыслу — `FromStep` перевязывается против выживших
  наблюдений вместо проигрывания значения, замороженного при планировании; `Literal` сознательно
  сохраняет и воспроизводит своё значение как есть — но старая фраза «`args_json` хранит `ArgSource`,
  а не значения» была ложна как прочитанная, и первый черновик спеки A1′ вывел из неё неверный вывод
  (спека §8.2). Не путайте два утверждения снова.
- **Идентичность C — деривация живёт в адаптере, не в `domain/tool`.** `ToolId(actionId.value)` пишется
  в `SystemIntentToolSource`, а `domain/tool` не получает нового импорта из `domain/action` ради этого
  (хотя `ToolDescriptor` уже импортирует `ActionArg`/`ActionRiskLevel` — см. «Долги… ЗАКРЫЛА» выше про
  исправленную формулировку). Только **проекции** биндятся так; `ActionIds` заморожен на семи значениях
  (ADR 3/4), у Tier-0-инструмента нет `ActionId`, и он чеканит свой `ToolId` сам.
- **Коллизия — первый адаптер в списке побеждает**, порядок — конструкция композиционного корня, не
  свойство `ToolLevel`. `DoctrineGuardTest` держит production-федерацию свободной от коллизий; сам
  рантайм-механизм — defence-in-depth, не единственная линия.
